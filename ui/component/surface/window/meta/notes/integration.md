# Подключение общего порядка окон

Механизм подготовлен изолированно от работающего Storybook. Его подключение
к приложению выполняется после завершения параллельной интеграции провайдера.

## Закон

HUD и каждый Display имеют собственное активное окно и собственный порядок окон.
Перевод keyboard focus в другую проекцию сохраняет активность предыдущей.
Сам keyboard focus остаётся единственным свойством общего Document.

Window регистрирует свою оболочку у ближайшей фактической проекции. ID проекции
не используется как ключ. Все Window этой проекции располагаются в одном
позиционированном родителе. При отсутствии проекции областью служит сам родитель —
это позволяет использовать тот же компонент в Headless и обычном контейнере.

## Композиция приложения

1. Создать общий позиционированный слой для целых Window внутри HUD или Display.
   Сам слой может находиться внутри обычной разметки приложения.
2. Перенести в него декларации окон соседями. Отдельные wrappers вокруг каждого
   Window убрать; размер и положение передавать через существующий geometry.
   Разные родители окон одной проекции отклоняются явной ошибкой.
3. Dock controls оставить вне слоя окон, в отдельном постоянном слое того же
   HUD или Display. Слой окон может иметь z-index 0, слой dock — z-index 1.
   Скрытие окна по-прежнему меняет controlled open, а не удаляет компонент.
4. Сохранение geometry/open/dock оставить приложению. Порядок и активность живут
   в текущем Experience и не требуют localStorage.
5. После подключения проверить реальным вводом A→B→A, dock, minimize/restore,
   перекрытие и переключение между HUD и несколькими Display.

Ранги z-index ограничены количеством открытых окон и меняются только при событиях.
Покадрового обхода нет. Ранг принадлежит внешней оболочке Window; разметка,
component regions и их порядок в DOM сохраняются. Это уточняет первоначальное
предложение о прямой перестановке DOM: compiled lifecycle окружает компонент
служебной областью, поэтому перемещение одной оболочки недостаточно.

Начальное монтирование делает активным последнее открытое окно каждой проекции,
сохраняя текущий keyboard focus. Последующее открытие возвращает последнее
доступное место ввода или фокус оболочки. Кнопка сворачивания не затирает
сохранённое место работы. Закрытие или удаление активного окна выбирает предыдущее
видимое окно своей проекции, сохраняя чужой keyboard focus.

## Проверки без рабочего браузера

Из корня worktree:

```sh
bun test --preload ./headless/preload.ts ui/component/surface/window/spec/scenario.spec.tsx ui/component/surface/window/test/activity.test.ts ui/component/surface/window-control/spec/scenario.spec.tsx ui/component/tests/window.test.ts
bun run --cwd ui/component/surface/window typecheck
```

Сценарий «Перекрытие окон» сверяет цвет пикселя в общей области до и после активации
на native WebGPU. Если задан WINDOW_LAYER_EVIDENCE_DIR, он сохраняет before.png
и raised.png туда. Остальные проверки используют настоящий compiled Component,
DOM, layout и hit testing: три проекции в одном Document, состояния полей,
выделение, scroll, перехват ввода, keyed reorder и освобождение компонентов.

Это свидетельства изолированной реализации. Визуальная проверка в рабочем
Storybook остаётся частью последующего подключения. Размытие включается обычным CSS `backdrop-filter: blur(8px)` в `style` Window.
Для видимого эффекта фон содержимого должен пропускать изображение: например,
`--space-node-navigation-background: rgba(40, 55, 80, 0.3)`. Радиус оболочки
задаётся `border-radius: 6px`. Нового пропса или режима Window не требуется.
Сценарий «Матовое стекло» показывает эту композицию и сравнивает контраст
с выключенным фильтром. Границы поддержки описаны у Renderer/WebGPU.
